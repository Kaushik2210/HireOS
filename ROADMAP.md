# HireOS Roadmap

Priority key: **Must** (MVP), **Should**, **Could**. Status is updated at each phase gate. Anything not yet built appears in the UI labeled "Planned".

| # | Phase | Priority | Status |
|---|---|---|---|
| 1 | Project foundation (tooling, lint, test setup, CI, design tokens, layout shell) | Must | Done |
| 2 | Authentication (Supabase Auth, protected routes, session expiry) | Must | Done (sign-up and isolation verified on a local stack; email confirmation and reset are not, see known issues) |
| 3 | Candidate profile (profile, skills, projects, certs, experience, preferences) | Must | Done (Supabase path verified on a local stack) |
| 4 | Resume upload and parser (secure upload, extraction, Resume Health) | Must | Done (Supabase path verified on a local stack; LLM-assisted parsing Planned) |
| 5 | Job database and providers (JobProvider, demo provider, dedupe, demo dataset) | Must | Done (no real provider by design; Supabase path verified on a local stack) |
| 6 | Job matching (Application Strength, breakdown, Job Intelligence page) | Must | Done (Supabase path verified on a local stack; weights uncalibrated; LLM explanations Planned) |

| 15 | Production polish, README, screenshots | Must | Done |

## MVP definition
Phases 1-7, 9 and 13 were the core path: sign in, build a profile or upload a resume, see ranked jobs with explainable strength, tailor a resume with verified claims, track applications. All fifteen phases are now built; what is left is listed under known issues and future improvements.

## Cross-phase items
- Command palette grows with each phase (Should; shell in phase 1, actions added as features land).
- Career Autopilot (flagship): needs phases 5-9; built after 9 as an Inngest pipeline ending in an approval queue (Should).
- Real job providers beyond demo: added one at a time after reviewing each source's terms (Should).
- Email sending via Resend after explicit approval (Could; drafts and copy first).

## Future improvements
Browser extension for user-initiated page capture, calendar integration for interviews, multi-resume A/B outcome analysis, additional LLM providers behind `LLMProvider`.

## Known issues
- `npm audit` reports 8 advisories, all in the dev-only Vitest toolchain (none in production dependencies; CI gates on `npm audit --omit=dev`). Upgrading Vitest is blocked by peer-dependency conflicts; revisit when the ecosystem catches up.
- Migrations are verified on PGlite in the test suite and, by hand, on a local Supabase stack (`npx supabase start`). A CI job running `supabase start` and `supabase db reset` is planned.
- Rate limits are shared through the database when the service role key is set, and fall back to per-instance memory otherwise or when the database is unreachable. The client address is read from `X-Forwarded-For`, so per-address limits are only as trustworthy as the proxy in front of the app.
- OAuth providers are Planned. Two-step sign-in (authenticator app) is built, with no recovery codes; it is enforced both by the app and, since migration 16, by the database (see SECURITY.md). Account deletion is built and does not ask for the password again.
- The Content Security Policy allows inline style attributes (`style-src-attr 'unsafe-inline'`); removing that means replacing the few inline widths with classes or CSS variables set another way.
- Demo sandboxes live in server memory: they reset on restart and are not shared across serverless instances.
- Profile items have no import path yet; resume parsing (Phase 4) will create unconfirmed items, and a confirm-all UI lands with it.
- Month inputs use the browser's native control, whose appearance varies by browser.
- The resume parser is heuristic. It handles the common layouts well (classic, pipe-separated, wrapped lines) but will misread unusual ones, such as multi-column designs, graphics-heavy templates and non-English resumes. It flags uncertainty and drops what it cannot read; all imported items need user review. An LLM-assisted fallback is Planned for after the `LLMProvider` interface exists.
- No OCR: image-only PDFs are reported as unreadable.
- Resume Health scoring weights and thresholds are initial values and have not been calibrated against real resumes. Resume Health keyword coverage is general breadth only; job-specific keyword coverage is part of Application Strength.
- Resume files are parsed in the request process. Move to a background job or isolated worker with the Inngest work in a later phase if volume warrants.
- Download is unavailable in demo mode because originals are discarded.
- **No real job provider is enabled, on purpose.** Before adding one I read Greenhouse's Job Board API documentation: it describes giving a company access to "your company's" offices, departments and jobs, to build that company's own careers page. It does not grant reuse by a third-party aggregator, so enabling it for other companies' boards would rest on an assumption rather than a stated permission. Lever and Ashby have the same shape. A real source should be added only when its terms clearly allow it (a licensed or partner feed, an API that explicitly permits aggregation, or a company that points its own board at HireOS), one at a time, with the basis recorded in its `termsNote`. Until then, real discovery is the "add a job" paste flow.
- The job provider framework, normalisation and dedupe are exercised by two fictional demo sources. The adapter surface for a real source is small: map its records to `RawJob`.
- Job analysis is heuristic. It reads conventionally written postings well (headed sections, bullets) and degrades to fewer extracted fields on prose-only or unusual ones; it never invents values. It cannot tell from text alone that "Go" in a sentence is the language, so very short skill names are only recognised in list contexts.
- Search is whole-word-fragment matching over title, company, location, skills and description, not full-text search with ranking or stemming ("engineers" does not match "engineer"). Fine at catalogue sizes in the thousands; move to Postgres full-text or trigram indexes when it grows. Title sort uses the database's collation, which may order punctuation differently from the demo store on a real Supabase instance.
- Pay is shown per posting in its own currency. There is no currency conversion and no salary sort.
- Ingestion has no scheduler yet: shared catalogue rows come only from `supabase/seed.sql` (demo) today. A refresh job (Inngest) arrives with the first real provider.
- Application Strength weights (30/15/15/10/10/10/10), the label thresholds (80/65/45) and the skills cap (below 40% of at least three required skills limits the total to 54) are reasoned starting values. They have not been calibrated against real outcomes and will change with evidence, which is why every result carries `scorer_version`.
- Skill matching is by canonical name and alias only. A related skill (for example Flask for Django) is never credited; it only appears as a suggestion on the gap. Level credit is a fixed table, not a measurement.
- Education requirements are read from the posting's text with patterns, so unusual phrasing may be missed (the education component is then left out rather than guessed). Experience is the sum of verified work and internship ranges with overlaps merged; leadership and volunteering do not count as years.
- Scoring is live: `/matches` and the dashboard score every visible job on each load (capped at 500). That is cheap at demo scale. A saved snapshot (`job_matches`) is written when a job page is opened and its profile hash or scorer version changed; nothing reads it for ranking yet.
- Explanations are built from templates over stored evidence. LLM-written explanations are Planned and will only reword evidence the scorer already produced.
- E2E timing: eight workers share one production server, and navigations sometimes took longer than Playwright's default 5 second assertion timeout (the add-a-job redirect and job detail loads were the usual victims, and failed the same way on the Phase 5 commit). A server-side timing check and a 48-navigation stress run found no slow or stuck request, so the cause is load on the test machine, not a hang in the app. The assertion timeout is now 10 seconds, link prefetching is off, and a redundant `revalidatePath` was removed from the add-job action; the suite has been green on repeated runs since. The resume upload failures that used to be blamed on load had two other causes, both fixed in Phase 14: the per-address upload limit (a real protection) was being used up by the test run itself, so each test now presents its own address, and a file chosen before the page had hydrated was silently dropped, so the helper now repeats the choice until the upload starts. That spec passes 108 of 108 over three repeats with no retries. The parser still runs in the request process (see above). If other tests start failing, check machine load first.
- Tailoring only chooses and orders verified items and copies their wording unchanged. It cannot make a weak bullet stronger, shorten a long one or adapt phrasing to a posting. LLM rewriting is Planned and will have to pass the same verifier (which blocks any reworded line today).
- Keyword matching for relevance uses the skill catalogue, so a skill that is not in the catalogue is never treated as relevant. A project with no catalogue skills is only chosen as a fallback.
- Resumes are plain text (copy and .txt download). There is no PDF or DOCX export and no template choice yet, and the profile has no email or phone field, so contact details come from the profile's location and links only.
- The cover letter is a short fixed-structure draft: a greeting, one project line, one role line, the matching skills and a closing, each quoted from the profile. It is deliberately plain; the user edits it. Edited text is checked for skills and numbers that are not in the verified profile, but the check cannot judge tone or implied claims ("led", "owned") in free wording.
- Version approval is the user's own review step and nothing more: it does not submit, send or share anything. Approved versions are immutable, including in the database.
- Outreach drafts are built from fixed templates around verbatim profile text. They are plain and short on purpose; they cannot adapt tone, mention something specific about the recipient or company, or vary between drafts. LLM wording is Planned and must pass the same verifier.
- Nothing is sent or connected: the person copies a draft into their own email or LinkedIn. "I sent this myself" is only their own record, so it cannot be checked, and nothing watches for replies. Follow-up reminders arrive with the application tracker (Phase 9).
- HireOS cannot check what the person types about a recipient or how they know them. A recipient's name and role are accepted as typed; the "how you know them" text is checked like the rest of the message, so a skill or number in it that the profile lacks is flagged.
- The follow-up and thank-you drafts say the person applied or spoke only after they tick a box saying so. The app cannot confirm either, and applications are not tracked until Phase 9.
- A LinkedIn note is limited to 300 characters, which is LinkedIn's connection-note limit for most accounts as of writing; accounts with a different limit would need that constant changed (`LINKEDIN_NOTE_LIMIT`).
- Drafts are hard-deleted (no soft delete or trash), and a draft keeps the wording it was written with even if the profile changes afterwards (a notice says so).
- Every status is the person's own record. HireOS reads no email, polls no employer site and sees no replies, so a status is only as accurate as what the person enters. "Applied" means they applied themselves on the employer's page.
- The board moves cards with a "Move to" menu that offers only the allowed next statuses, not by dragging. It works with a keyboard, a screen reader and a phone; drag and drop is Planned.
- The follow-up engine is derived, not stored: an awaited application (applied, assessment or interview) is due after seven quiet days, or on the date the person set. The seven days is a constant (`DEFAULT_FOLLOW_UP_DAYS`), not yet a setting, and there are no reminders, emails or notifications: it appears on the board, the application page and the dashboard. The planned `followups` table was not needed.
- The allowed moves (for example Rejected is final, Offer can only become Rejected or Withdrawn) are a first design. A real search may need others, such as reopening a rejection. The rule lives in one table that the app, the demo store and the database tests all check.
- An application keeps its title, company and history when its job is deleted, but then has no link back to the job and cannot start a follow-up draft.
- Contacts (`contacts` in the original data model) are not built: recruiter names live in notes and in outreach drafts. They would arrive with analytics if the data is worth structuring.
- Sample applications are generated for each demo visitor from fixed definitions dated relative to now. They exist only in demo mode, are clearly labelled, and can be cleared with one button.
- Practice scoring judges how an answer is built, not whether it is right. It checks shape (STAR for experience questions; definition, reason and example for concept questions), concrete detail, topics the question usually calls for, ties to your own verified work, length and clarity, and honesty about your profile. It cannot tell a correct technical answer from a wrong one, understand meaning, or predict how any interviewer would react, and it can be gamed by writing the right words. The weights are equal and uncalibrated. An AI coach that reads answers is Planned and would have to stay rule-bound and hedged.
- The question bank is small and hand-written (39 technical questions across 30 catalogue skills, 8 behavioral and 3 motivation questions). A posting whose skills are not in the bank gets general questions (data structures, SQL, Git) instead. The "topics" a question expects are prompts, not an answer key.
- Practice is typed. There is no voice, video, timer or speech analysis, and a session is not resumable across a different question order: it asks the questions it saved, in order.
- The prep checklist is a set of suggestions from the posting and your verified profile. It does not know what the interviewer will ask, and gaps are only phrased as "be ready to say plainly that you have not used X yet".
- A round's date and time are the person's own wall-clock values with no time zone, and nothing is added to a calendar or reminded. Rounds are not linked to application status: moving an application to Interview is a separate step.
- Contacts and interview outcomes (for analytics) are not modelled separately: the interviewer is free text and notes hold the rest. Phase 11 may want a structured outcome.
- Analytics are only as good as what the person records. HireOS sees no email or employer site, so every reply is something they entered. Rates use "n of m" and are flagged as a small sample below ten applications; with fewer than five, "Why am I not getting interviews?" says there is not enough data and shows only what the records support.
- The "why" findings are patterns, never causes. They use hedged wording ("may have", "likely contributing"), list their evidence, and end with a caveat that employers decide for reasons that are not visible here. They cannot weigh things the data does not hold (referrals, luck, timing, the other applicants), and whether following up helps is stated as uncertain.
- Application Strength in the analytics (by fit, repeated gaps) is measured against the profile as it is today, not as it was when the person applied, so a later profile change shifts old numbers. The page says so.
- Career Gaps measures each missing skill by re-scoring up to 30 jobs (the ones tracked, then the best matches) with the skill added in a simulation. It does not know how hard a skill is to learn, how long it takes, or which employers really care, and it does not recommend courses or resources: it says to build something real and add the skill once it is true. Skills outside the catalogue cannot be measured.
- Career readiness combines profile completeness, the latest resume's health score and the share of the top ten jobs rated Good or Strong, with equal care for what cannot be measured yet (a missing part is left out, not guessed). The weights (40, 30, 30) are uncalibrated.
- Analytics read live on each visit: nothing is stored or cached, so very large histories (hundreds of applications) will slow the page. The activity read is capped at 2,000 events.
- No outcome data beyond status is modelled (for example why a rejection happened, or offer details), so there is no salary or offer analysis yet.
- The career graph is a picture of records, not an analysis: it does not rank or score anything, and a connection means "is in your data", not "matters". Jobs shown are the ones you track plus your best matches, at most twelve, and at most six required skills per job, so it is a sample of the job market rather than all of it. Past 160 items the least connected skills are left out and the page says so.
- The layout is a deterministic force simulation computed on the server (no randomness, so a reload does not shuffle it). With a few dozen items it is readable; with more it gets crowded and relies on the filters, zoom and the list view. Skill and company names are hidden until zoomed in or related to the selection. There is no free dragging of nodes, no saved positions and no export of the picture.
- The graph has no history: it shows today's profile and today's matches, and cannot show how the person's skills or applications changed over time.

- **Verified live (Phase 15).** The live suite (`npm run test:live`, see TESTING.md) runs the profile, job, resume (with storage), document, outreach, application, interview, practice and match stores against a real local Supabase as two real accounts, and passes (10 tests). It found and fixed two bugs the fakes had hidden: saving the profile or career goals, and saving a match snapshot, used an upsert that PostgREST turns into an update of `user_id`, which the database rightly refuses clients. Both are now an update followed by an insert.
- **Not verified live:** email confirmation and password reset (the local stack's mail catcher is not wired in), sign-in through the browser beyond a manual sign-up, and anything on a hosted Supabase project. The Auth settings that matter there (confirm email, leaked-password protection, redirect allow-list) are dashboard settings to check by hand.
- Automated accessibility checks (axe) pass on every main page at desktop and phone width. They find a fraction of real problems: keyboard-only and screen-reader use have not been tested by a person.
- Phase 14 found and fixed two quadratic-time patterns (markup stripping and email/salary scans in job and resume text); robustness tests now guard every text-handling function against unclosed markup, long unbroken words and floods of blank lines.
- **Hosted demo.** Deployed to Vercel in demo mode (no keys, no database) at https://hireos-beryl.vercel.app; pushes to `main` redeploy it through the connected GitHub repository. Demo sandboxes live in server memory, so on serverless hosting they can reset when an instance is replaced or a request lands on another one (12 of 12 reloads kept an edit in a manual check, which is not a guarantee). A hosted Supabase project is the fix and has not been set up.
- The README screenshots are of the fictional demo candidate and sample jobs; regenerate them with `npm run screenshots` after UI changes. The project is MIT licensed (see LICENSE).
- The CI `live` job (a local Supabase stack, `supabase:check` and the live suite) is written but has never run: nothing has been pushed to GitHub, so none of the CI jobs have run there yet.
